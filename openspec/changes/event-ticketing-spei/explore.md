# Exploration: event-ticketing-spei

Date: 2026-10-04. Real event deadline: 2026-10-30.

## Product decisions (from brainstorm with organizer)
- Replace RSVP (Attendance.responseType confirmed/maybe/declined + Confirmation table) with a Ticket model.
- Google-Forms-like custom form per event; email is a fixed mandatory field (ticket is emailed there).
- Event has a price; organizer enables payment methods per event: SPEI and/or cash. Public sees ONLY SPEI. Cash is used only by the host registering walk-ins at the door (same single door price for all methods).
- SPEI flow: register -> "registration received" email with link to upload receipt -> attendee uploads receipt -> pending_validation -> organizer approves/rejects -> on approval, email with ticket + QR. Rejected -> email to re-upload. Ticket/QR is emailed ONLY after approval.
- Lifecycle: pending_receipt -> pending_validation -> paid -> checked_in (+ rejected, cancelled). Door + cash -> paid + checked_in instantly.
- QR = signed token (HMAC-SHA256), single-use at check-in; short human code (e.g. EVT-7K3Q) for manual search.
- Host scanner: scan QR or search by name/code -> see attendee info, answers, payment status -> check in. Second scan shows "already checked in at HH:MM".
- Dashboard attendee list with status filters, search, export.
- Public ticket page shows only the ticket/QR, no navigation back to events. Buttons: share EVENT link (Web Share API + copy fallback) and download ticket PDF.
- Ticket visual design (template, bg/text/accent colors, logo, header image) configured by organizer only.
- Event supports multiple images as an auto-advancing carousel.
- No payment gateway for now (MP/Stripe dropped); keep payment behind a port for future adapters.
- Vitest to be added for critical domain logic (token signing, short code, status transitions, form schema validation).

## Product question round (answers)
- Email: organizer already has a Resend account and a subdomain; emails sent under codeverse.com.mx. Use Resend. Confirm domain shows "Verified" (SPF/DKIM) in Resend before slice 1 ships.
- One ticket per person: each registration = 1 ticket with its own form + email. Unique (eventId, email). Re-registering with an existing email resends the existing ticket's link (upload receipt / view ticket) instead of creating a duplicate.
- Capacity is organizer-controlled: optional internal `capacity` (never shown publicly) auto-closes public registration when reached; counts tickets in pending_validation + paid + checked_in (pending_receipt does NOT hold a spot). Manual `registrationOpen` toggle to close anytime. Public capacity display is decoupled from the real cap (organizer may show a different marketing number, or nothing). Door registrations by host ignore the cap.
- Multiple door staff, each on their own phone. CONFIRMED: per-event "door access" link + PIN generated by organizer (no accounts); staff enter their name on open (stored as checkedInBy for audit); can scan, search, check in, register walk-ins with cash; CANNOT see receipts, revenue or event settings; organizer can revoke/regenerate.

- Defaults accepted by organizer:
  1. SPEI details (CLABE, bank, beneficiary) configured per event; transfer concept = ticket short code.
  2. Free events (price 0): no payment step; ticket + QR emailed immediately.
  3. Form editing with existing tickets: may add fields and edit labels; cannot delete fields that have answers.
  4. Receipt: image or PDF, max 5MB, stored privately (owner only; never staff, never public URL).
  5. Rejection: organizer writes reason; attendee gets email to re-upload.
  6. Legacy RSVP data discarded (nothing in production).
  7. Timezone: display in America/Mexico_City.

## Uploads / receipts
- app/api/upload/cloudinary/route.ts: session required, images only (jpeg/png/webp/gif), 5MB, returns PUBLIC secure_url. Not usable for receipts.
- Recommended: receipts stored privately in Postgres (Receipt table, bytea, mime, size), served via owner-checked route handler; magic-byte validation JPEG/PNG/WebP/PDF, ~5MB cap; public token-gated upload route handler (server actions have 1MB body limit), rate-limited. Cloudinary stays for public event images and ticket design assets.

## Approaches (recommended)
- Email: Resend behind a sendEmail() adapter (SMTP fallback). Needs verified domain (DNS lead time). Never fail registration on email error; record emailSentAt, allow resend.
- PDF: @react-pdf/renderer server-side (small template set), attachable to approval email. Fallback html-to-image.
- QR scanning: @yudiel/react-qr-scanner (verify React 19 peer); HTTPS required; always manual search fallback.
- QR token: HMAC-SHA256 with node:crypto + timingSafeEqual; atomic check-in `updateMany where {id, status: paid}` count 0 = already used. Crockford alphabet short code, unique + retry.
- Form builder: `formSchema Json` on Event (versioned, validated), answers JSONB on Ticket keyed by stable field ids + label snapshot. email (and name) first-class columns. v1 field types: short text, long text, select, checkbox, number, phone. Lock: once tickets exist, only add fields / edit labels.
- Model sketch: Ticket(id, eventId, code unique, email, name, answers Json, status enum, paymentMethod enum SPEI|CASH, amount Int cents, receiptToken, checkedInAt, checkedInBy, rejectionReason, createdAt), Receipt(id, ticketId, bytes, mime, size, uploadedAt), EventImage(id, eventId, url, position), Event += price cents, currency, allowSpei, allowCash, speiClabe/bank/beneficiary, formSchema Json, ticketDesign Json, capacity?.
- Tests: Vitest + vite-tsconfig-paths, node env; pure logic in lib/. Run with `bunx vitest run`.

## Risks
1. Deadline (26 days) -> slice: Slice 1 presale (~10/12), Slice 2 event day (~10/24), rehearsal ~10/26.
2. Email domain verification is the top schedule blocker — start immediately.
3. BUG: updateEvent regenerates slug on every edit (L136, L143) — breaks shared links. Fix first.
4. BUG: updateEvent blocks edits for past date/time (L129-134) — organizer can't edit/cancel on event day.
5. Upload route auth-only/image-only/public URLs — new receipt route needed.
6. Privacy of receipts + PII; no public URLs, consider post-event purge.
7. Abuse: no rate limiting on public endpoints; dedupe policy (one ticket per email vs quantity) undecided.
8. Free events (price 0) behavior undecided. Block publishing if price > 0 and no method enabled.
9. Capacity / overselling undecided.
10. Concurrency: atomic check-in; idempotent approval (no double emails).
11. Timezone: pin display to America/Mexico_City.
12. Ticket page in its own route group/layout (e.g. app/ticket/[token]) with no nav.
13. Web Share API needs HTTPS + gesture; copy-link fallback.
14. Housekeeping: dead files, Confirmation table, two lockfiles, uncommitted changes in working tree.
